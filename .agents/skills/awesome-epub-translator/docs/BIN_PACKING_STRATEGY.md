# 智能分發：Size-aware Bin Packing 策略

在多代理 (Multi-Agent) 平行處理大型電子書的過程中，任務分配的均勻度直接影響了系統的穩定性與執行效率。如果僅採用「循序分配」或「無腦均分檔案數量」，很容易發生某個 Subagent 分配到過多超大章節，導致 Context Window 爆滿、產生幻覺 (Hallucination) 或直接崩潰 (Timeout)。

為了徹底解決這個問題，主 Agent 實作了一套基於貪婪演算法的 **Size-aware Bin Packing（依檔案大小組裝任務）** 策略。

## 演算法步驟解析

### 1. 測量與排序 (Measure & Sort)
在每一回合 (Round) 開始時，主 Agent 會針對所有「尚未翻譯」的 XHTML 檔案執行 `wc -c` 來取得精準的位元組大小 (Bytes)。
取得大小後，將這些檔案**「由大到小」遞減排序 (Descending Order)**。此舉是為了確保最龐大、最耗資源的檔案能被優先處理並分散。

### 2. 設定邊界條件 (Define Constraints)
系統預設啟動最多 3 個 Subagent（相當於 3 個處理容器 / Bins）。為了防止單一 Subagent 認知超載，每個容器設有嚴格的容量限制：
* **數量上限**：最多 3 個檔案。
* **體積上限**：總和不超過 ~200 KB。

### 3. 貪婪分配 (Greedy Assignment)
取出排序好的檔案清單，針對每一個檔案執行以下分配邏輯：
1. 檢查 3 個 Subagent，找出目前 **「累積檔案大小最小」** 且 **「未達上限」** 的那一個。
2. 將該檔案分配給這個 Subagent。
3. 重複此動作，直到所有檔案分配完畢，或是 3 個 Subagent 都已達到上限。

> **優勢**：透過由大到小的貪婪分配，最大的幾個檔案必定會被打散分配給不同的 Subagent，達到完美的負載平衡 (Load Balancing)。

### 4. 邊界情況處理 (Edge Cases)

* **剩餘檔案處理 (Leftovers)**：
  如果 3 個 Subagent 都已經裝滿（無論是觸及 3 個檔案上限還是 200KB 體積上限），但清單上仍有剩餘檔案，主 Agent **不會**強行分配。這些剩餘的檔案會直接被留在清單中。當這一回合的 3 個 Subagent 處理完畢後，主 Agent 會在下一回合開始的「目錄掃描」中，再次將它們納入新的 Bin Packing 流程中。

* **單一檔案直翻 (Single File Optimization)**：
  如果到了整個任務的尾聲（或是電子書本身極小），待翻譯檔案只剩下 **1 個**。主 Agent 為了節省喚醒 Subagent 的初始化與 API 往返開銷 (Overhead)，會跳過派發流程，直接在自己的 Context 中執行翻譯。

## 常見疑問與概念釐清

### 1. 章節與 XHTML 的對應關係
在 ePub 的標準架構中，ePub 本質上是一個被壓縮的微型網站。為了避免電子書閱讀器（如 Kindle、Kobo 或手機 App）在翻頁或調整字體大小時，需要一口氣重新計算數百頁的排版而導致卡頓甚至當機，**出版商通常會強制將書籍內容切分，讓「一個 XHTML 檔案」剛好對應「一個章節」**。這也是為何在多數情況下，單一 XHTML 檔案不會無限制膨脹（業界實務通常小於 300KB），因為每一次跨章節的翻頁停頓，其實就是閱讀器在載入並渲染下一個 XHTML 檔案。

### 2. 若單一章節超大怎麼辦？（輸入與輸出的雙重防護）
儘管多數章節檔案不大，但若遇到極端龐大的 XHTML 檔案，系統除了依靠上述的 Bin Packing 策略將該檔案「單獨隔離」給單一個 Subagent 專心處理外，還會利用 **記憶體內分批處理 (Batch Processing)** 來克服 AI 的物理限制：

* **輸入 (Input) 階段的全局視野**：
  Subagent 會先呼叫工具讀取整個 XHTML 檔案。現在的 AI 擁有龐大的 Context Window（吸收能力），一口氣讀完全文能讓 AI 理解文章的全貌、角色與脈絡，不會因為見樹不見林而翻錯。
* **輸出 (Output) 階段的分批產出**：
  與強大的讀取能力不同，AI 的「單次輸出字數 (Output Token Limit)」有著嚴格上限。如果強迫 AI 一次寫完幾萬字的譯文，必定會導致文字生成到一半被強制截斷，破壞 HTML 的標籤結構。
* **「看大全、寫小塊」策略**：
  因此，Subagent 雖然一眼看完整篇文章，但在產出時，會在腦海（記憶體）中將長文切分成每次約 2000~3000 字元的小區塊分批翻譯，並保留上一批的幾句話作為上下文確保語氣連貫。
* **一次性寫回硬碟**：
  為了確保檔案結構完整，Agent **不會**每翻譯一段就寫入檔案一次。它會等所有區塊都在記憶體中翻譯並拼接完畢後，才「一次性」將帶有完整閉合標籤的 XHTML 寫回硬碟，徹底杜絕半成品造成的檔案損毀。


大致流程：

* **主 Agent 的角色（專案經理）**：在喚醒 Subagent 時，會將 `SKILL.md` 中定義好的「強制寫入策略」與「分批規範」作為鐵律 (System Prompt) 注入給 Subagent。
* **Subagent 的實際執行迴圈**：
  收到 SOP 後，Subagent 會嚴格執行以下標準生命週期：
  1. **接收 SOP**：收到指定的 XHTML 檔案路徑、風格畫像，以及「必須分批翻譯、最後一次寫入」的鐵律。
  2. **全域讀取**：使用工具 (`view_file`) 讀取整個檔案，了解文章全貌與 HTML 結構。
  3. **分批產出**：在腦海中將文章切分為每次約 2000~3000 字元的批次。每翻譯下一批時，會保留上一批的結尾作為上下文，確保語意不斷層。
  4. **一次性寫入**：將腦海中所有翻譯好的批次重新拼裝成完整的 HTML 結構，最後才呼叫一次工具 (`write_to_file`) 將成品寫回硬碟。
